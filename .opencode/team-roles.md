# Роли команды в OpenCode

Лид координирует реализацию, архитектуру, дизайн и ревью. Источник знаний —
CONCEPT.md, DECISIONS.md, specs, BOARD.md и BACKLOG.md. Перед работой читать
их и AGENTS.md; внешняя память необязательна.

Для независимых параллельных задач использовать Ensemble: создать команду,
завести задачи и зависимости по возвращённым ID, выдать каждому исполнителю
отдельный worktree, границы файлов и критерии приёмки. Начинать с двух-трёх
исполнителей. team_message служит для прямой переписки, team_broadcast —
для общих фактов. Перед интеграцией проверить результаты, ревью и гейты проекта.
Статус done не разрешает слияние в main. mergeOnCleanup выключен: интеграция
веток выполняется явно с сохранением неслитой работы. BOARD.md и BACKLOG.md —
основной учёт проекта, задачи Ensemble — учёт исполнения без второго бэклога.

Архитектор .opencode/agents/architect.md работает только на чтение. Вызывать
@architect для вариантов решений, компромиссов, ревью и проектов ADR. Модель
наследуется от вызывающего агента, если не указан provider/model-id. Дизайнер
необязателен: можно использовать модель с изображениями или отдельно настроенный
MCP. Методика не требует конкретного провайдера, подписки или дизайн-сервиса.

После обновления файлов агентов перезапустить OpenCode. Провайдеры и модели
настраивать в пользовательской конфигурации; ключи не коммитить. Дашборд Ensemble
показывает сообщения и задачи. Переписка действует внутри команды; связь между
независимыми командами не предполагается. Worktrees не исключают merge-конфликты.

Стандартная команда: техлид (tech-lead), аналитик/архитектор (architect), UX/UI-дизайнер (designer), фронтендер (frontend), мобильный разработчик (mobile), бэкендер (backend), тестировщик (tester), ревьюер (reviewer), DevOps (devops). Все девять ролей поставляются в .opencode/agents; техлид подключает нужных участников под задачу.

## Предложил → человек решил → ADR

1. Архитектор читает CONCEPT.md, DECISIONS.md, релевантные specs, BOARD.md и
   BACKLOG.md. Возвращает контекст → варианты с компромиссами → рекомендацию →
   открытую развилку, называет использованные файлы и предлагает ADR-Lite
   в формате DECISIONS.md. Read-only консультант не пишет код и не решает за человека.
2. Нерешённую продуктовую или архитектурную развилку лид передаёт человеку через
   интерактивный question: рекомендация первой, последствия каждого варианта.
   Только tech-lead имеет question:allow; все восемь специалистов — question:deny
   и передают вопросы лиду через team_message. Рутинная реализация и следующие
   итерации в уже согласованном scope нового разрешения не требуют.
3. Человек выбирает; лид/человек вносит финальную запись в DECISIONS.md.
   Предложение архитектора и done исполнителя не заменяют решение и приёмку.

## Дизайнер и границы перевода

Дизайнер подключается для интерфейса, прототипа и визуальной спецификации;
получает бриф specs/design-brief-template.md и итерирует его с лидом. Его HTML/CSS/JS
или иной макет — спецификация, не автоматически реализация целевого UI-стека:
перенос делает назначенный frontend/mobile исполнитель в отдельном согласованном
шаге. Отдельный MCP, подписка, внешний Design-сервис и конкретная модель не нужны
для начала работы. Лид выбирает только нужные роли, а не запускает все девять.

## Нативные контроли и продолжение незавершённой работы

- AGENTS.md автозагружается OpenCode; opencode.json.instructions дополнительно
  загружает этот файл. Роли обнаруживаются из .opencode/agents/*.md.
  Отдельных project commands/rules в исходном проекте и rendered 2.0.0 нет:
  рабочие команды и правила содержатся здесь, в AGENTS.md, hook и guard.
- architect/reviewer — deny-by-default, только read/glob/grep/list и командная
  переписка/учёт; запускать с worktree:false. Shell, edit, внешние MCP и вопросы
  им не разрешаются. Права новой сессии не доказаны одним наличием файлов:
  текущая сессия продолжает работать с уже загруженной конфигурацией.
- На каждый раунд лид фиксирует exact base SHA, ownership, AC; автор сначала
  проверяет HEAD и clean status своего свежего worktree. Выравнивать можно только
  такой worktree. Чужие и dirty checkout неприкосновенны.
- До shutdown получить commit SHA, scope и dirty state; сохранить unfinished.
  Для Ensemble0.18.0 shutdown предшествует team_merge. Shutdown терминален:
  следующий раунд — новый уникальный автор от checkpoint интеграции; отметить
  ожидаемые failing tests. Не изображать force-delivery как resume.
- После прерывания на devbox проверить dt recover <project>; resume только exact
  --member, --lead-session, --task. HTTP timeout не означает отсутствие эффекта:
  сначала сверить состояние. Exactly-once и автоматическое восстановление от
  любого сбоя не обещаются. Один постоянный сервер, клиенты attach; не перезапускать
  активную команду для применения этих файлов. Новая конфигурация — после штатного
  завершения и нового старта, отдельно от нынешнего rollout.
- Незавершённая T015 остаётся в BOARD.md Doing до полного review/CI; текущие
  исходные свидетельства devops-r1 — specs/T015-dreamteam-200/rollout-preflight.md,
  продолжение r2 — rollout-manual.md рядом. Это continuity реальной открытой
  задачи, а не обещание восстановления любого task.
- Gates: ruff check ., ruff format --check ., mypy src tests scripts;
  полный pytest с Xvfb через scripts/pytest-guard.sh, coverage80. GitHub CI
  сохраняет Windows build/smoke. srv onboarding не подтверждён; иной CI не вводить.
