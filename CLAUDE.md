# Project rules for Claude

Этот файл — проектные правила для Claude (Claude Code). Глобальные
правила (`~/.claude/CLAUDE.md`) применяются всегда; здесь — только то,
что специфично для конкретного проекта.

## Что прочитать в начале сессии

1. `CONCEPT.md` (если есть) — изначальное видение проекта,
   immutable документ. Полезен как точка опоры через месяцы.
2. `README.md` — текущее описание / quick start / status проекта.
3. `DECISIONS.md` — архитектурные решения, которые уже приняты.
4. `BACKLOG.md` — что лежит в очереди.
5. При работе над крупной фичей — соответствующий `specs/T<NNN>-*/spec.md`.

## Ритуал составления `CONCEPT.md` (для нового проекта)

В начале нового проекта Claude помогает Разработчику составить
`CONCEPT.md` — immutable документ начального видения. Это ритуал
встречных вопросов, аналогичный `clarify` для спеки:

1. Разработчик пишет первый набросок (или формулирует идею).
2. Claude задаёт встречные вопросы по слепым зонам:
   - **Цель:** какую боль / задачу проект решает?
   - **Пользователь:** кто, в каком контексте?
   - **Ключевая функциональность:** MVP-минимум vs nice-to-have?
   - **Out of scope:** что СОЗНАТЕЛЬНО не делаем? (главный раздел
     для защиты от scope creep).
   - **Ограничения и догадки:** платформа, стек, нагрузка,
     ассумпции.
3. Ответы вшиваются в `CONCEPT.md`, проставляется дата создания.
4. **После фиксации `CONCEPT.md` не редактируется.** Текущее
   состояние ведётся в `README.md`. Если концепция кардинально
   меняется (rare, pivot) — добавляется `concepts/v2-...md`,
   `v3-...md` (ADR-pattern, но для концепций).

**Структура — опросник, а не contract.** Разделы выше (Цель /
Пользователь / Ключевая функциональность / Out of scope /
Ограничения) — это **leading questions для пустого `CONCEPT.md`**, а
не обязательная форма финального документа. Если в проекте уже есть
содержательный `CONCEPT.md` / ТЗ / vision в любой форме — Claude
**принимает его как есть** и проводит `clarify` по слепым зонам его
содержимого, **не требуя** перекладки в шаблонные заголовки.
Единственный обязательный элемент ритуала — **clarify** (встречные
вопросы). `Out of scope` остаётся самым ценным разделом (защита от
scope creep), но может быть выражен в любой форме внутри уже
существующего документа. Immutable-инвариант (после фиксации не
редактируется) сохраняется в любом случае.

Заполнение `CONCEPT.md` — на этапе создания проекта через
`dreamteam init` (Claude задаёт встречные вопросы) или позже,
вручную.

**Базовый стек шаблона (для Python-проектов):**
- Python 3.14+ (`requires-python` в `pyproject.toml`).
- Менеджер зависимостей и окружений: **`uv`** (выбран
  при `dreamteam init` через prompt `package_manager`; альтернативы:
  `uv` / `poetry` / `pdm` / `hatch` / `pip`).
- Линтер: `ruff` (правило `select = ["ALL"]` с фиксированным `ignore`).
- Тип-чекер: `mypy` с `mypy_path = "src"`.
- Тестовый стек: `pytest` + `pytest-cov` + `pytest-asyncio`. Coverage
  threshold ≥ 80% line coverage на `src/` (`--cov-fail-under=80`). Порог
  держится **явной командой** в pre-push-гейте и CI, а не в дефолтном
  `addopts` — дефолтный `pytest` намеренно лёгкий (см. раздел «Тяжёлые
  тест-прогоны — через мьютекс-обёртку» ниже).
- **Корень исходников — `src/`** (всегда, во всех проектах).
- Тесты — в `tests/` в корне (в ruff `exclude`, но pytest их
  находит через `testpaths = ["tests"]`).

**Типичные команды (для выбранного `uv`):**
- `uv sync` — поставить зависимости (создаст `.venv` при первом запуске).
- `uv add <pkg>` / `uv add --dev <pkg>` — добавить runtime / dev зависимость.
- `uv run python ...` — запустить под `.venv` без активации.
- `uvx <tool>` — запустить CLI-инструмент без локальной установки.

Перед каждым `git push` обязательно **четыре** проверки с 0 ошибок:
1. `uv run ruff check .`
2. `uv run ruff format --check .`
3. `uv run mypy <код>`
4. `scripts/pytest-guard.sh --cov=src --cov-report=term-missing --cov-fail-under=80`
   — полный прогон с порогом покрытия ≥ 80% **через мьютекс-обёртку**
   (см. раздел «Тяжёлые тест-прогоны — через мьютекс-обёртку» ниже).

**Запускать одной цепочкой**, чтобы fail на любом шаге прерывал
commit:

```bash
uv run ruff check . && \
uv run ruff format --check . && \
uv run mypy <код> && \
scripts/pytest-guard.sh --cov=src --cov-report=term-missing --cov-fail-under=80 && \
git add -A && git commit -m "..." && git push
```

**Catch-it-at-the-output:** если в выводе предыдущей команды
видишь `FAILED`, `Error`, `1 failed` или подобные маркеры —
**не двигайся дальше**, проверь причину. И не глуши exit-code:
`pytest | tail -5` возвращает exit-код `tail`, не `pytest` —
fail незаметно проскочит в `git commit`.

Никаких `# noqa` / `# type: ignore` / расширений `ignore`-секций
без явного обсуждения с Разработчиком. Подробно — в глобальном
`~/.claude/CLAUDE.md`, разделы «Линтеры» и «Тестирование».

## Тяжёлые тест-прогоны — через мьютекс-обёртку

Когда несколько `git worktree` делят одну машину (см. раздел
«Параллельная работа в нескольких git worktree» ниже), общий ресурс —
**оперативная память**. Полный / coverage-прогон держит заметный RSS;
два-три одновременно (рядом с тяжёлой IDE) стекаются в **OOM или
зависание**. Обёртка `scripts/pytest-guard.sh` сериализует тяжёлые
прогоны между ВСЕМИ worktree через общий per-user lock (concurrency 1,
блокирующее ожидание: второй прогон ждёт очереди и стартует сам).
Сериализуется только **запуск** — код и незакоммиченное состояние
сессий не трогаются.

**Правило — что через обёртку, что напрямую:**

- **Полный / coverage-прогон и pre-push тест-гейт — через обёртку**
  (`scripts/pytest-guard.sh …`), а не голым раннером; особенно при живых
  параллельных сессиях.
- **Точечный однофайловый прогон** (лёгкий, разовый) — можно напрямую
  (`uv run pytest tests/test_x.py`); мьютекс не обязателен.
- **CI — напрямую** (изолированный раннер, делить нечего).

**Лёгкий дефолтный прогон.** Coverage вынесен из дефолтного `addopts`
(трассировщик покрытия раздувает RSS/CPU): дефолтный `uv run pytest`
остаётся лёгким для повторяющейся локальной итерации. Порог ≥ 80%
сохранён — просто держится **явной командой** (гейт 4 выше и CI), а не
в дефолте.

**Опциональный лимит памяти на прогон.** Переменная
`PYTEST_GUARD_MEM_MAX` (напр. `4G`; `0` или не задана — выключено):
на Linux с systemd-сессией прогон запускается в транзиентной cgroup с
лимитом RSS, чтобы кривой тест убивался OOM-killer'ом **внутри своей
cgroup** (падает прогон, а машина и IDE живут), а не ронял систему. Вне
Linux/systemd (macOS, Windows, контейнеры) — no-op, прогон всё равно
идёт через мьютекс.

**Кроссплатформенность.** `flock` — util-linux (Linux / macOS-подобные).
Где его нет (Windows) обёртка **деградирует корректно**: печатает одну
строку-уведомление и запускает прогон напрямую (без сериализации), не
падает.

## Git workflow

Базовые правила процесса (применяются в этом проекте всегда):

- **Задачи нумеруются.** Каждая запись в `BOARD.md` / `BACKLOG.md`
  имеет ID `T<NNN>`; ветка — `T<NNN>-<slug>`; PR — `T<NNN>: <title>`.
  Исключение — методические PR, меняющие сами правила (без `T`-ID).
- **Прямой push в `main` / `master` запрещён.** Любое изменение — через
  feature-ветку и PR/MR.
- **Один PR — один коммит.** На feature-ветке можно коммитить как
  удобно для работы, перед merge — squash.
- **Закрытие задачи — в её же PR.** Перенос записи из `BOARD.md →
  Doing` в `Done` делается **в том же squash-коммите** задачного PR,
  а не отдельным chore-PR (после merge задача и так Done — `BOARD.md`
  просто отражает реальность). Границы PR — по логической связности
  задачи; дробить связные изменения ради «PR покороче» — anti-pattern
  (лишний overhead на review, расход квоты ревью-ботов).
- **Каждый PR проходит code review** перед merge. Если в проекте
  подключён рабочий автоматический ревью-бот (CodeRabbit,
  qodo-code-review или аналог, ревьюящий каждый PR) — он и есть
  baseline, **отдельный self-review Claude'а по умолчанию не
  требуется**. Self-review Claude'а нужен в трёх случаях: (1) **docs
  / методика** — PR, меняющий только markdown / правила / спеки (боты
  слабо ревьюят прозу) → self-review остаётся дефолтом; (2)
  **нетривиальный код** — targeted deep-review по зоне риска
  (архитектура, безопасность, сложный scope), по запросу Разработчика
  или инициативе Claude; (3) **fallback** — бот недоступен
  (rate-limit, лёг, не отчитался в разумном окне). Чеклист
  self-review: scope / архитектура / код / линтеры / документация /
  соглашения / безопасность.
- **Сторонние ревью не игнорировать.** Боты типа CodeRabbit /
  qodo-code-review — читать, анализировать, обсуждать с Разработчиком;
  фиксировать решение (учесть / отбросить / отложить).

## Дисциплина планирования

Без Scrum-церемоний (sprints, story points, velocity, burndown).
Поддерживаем только полезные элементы:

- **Milestone-based versioning.** `[Unreleased]` в `CHANGELOG.md`
  накапливает изменения. Переход к новой версии `[N.M.0]` —
  когда **осмысленно завершено** (soft criterion): введены значимые
  изменения, ИЛИ завершён логически связанный цикл задач, ИЛИ
  накопилось «достаточно» для отдельной точки сохранения.
  Окончательно решает Разработчик; формальной метрики нет — она
  противоречит самому принципу «без Scrum-карго». Формат версий —
  Keep a Changelog (`## [N.M.0]`, без `v`-префикса).
- **Retrospective как ритуал** после закрытия milestone. Короткий
  разбор в формате трёх пунктов:
  - что зашло (work-as-expected, или приятный сюрприз),
  - что не зашло (boundle, slip-ы, лишний overhead),
  - правки методики (что менять в `~/.claude/CLAUDE.md` /
    проектном `CLAUDE.md` / шаблоне).
  Размещение: **секция `### Retrospective`** внутри записи
  соответствующей версии в `CHANGELOG.md`. Не отдельный файл —
  ретро тесно связан с milestone, удобно читать рядом.
- **Acceptance criteria** обязательны для задач крупнее однострочной
  правки — записываются прямо в `BOARD.md` / `BACKLOG.md` коротким
  блоком (`Acceptance: <что должно быть достигнуто, чтобы задача
  считалась закрытой>`) или в `specs/T<NNN>-*/spec.md` для крупных
  фич. Без явных acceptance criteria задача не считается зрелой
  для перехода `BACKLOG → BOARD → Doing`.
- **WIP-limit** в `BOARD.md → Doing`: максимум 1-2 задачи. Больше —
  теряется фокус (классическое kanban-правило).

Если у Разработчика настроен глобальный `~/.claude/CLAUDE.md` —
там лежит расширенная версия этих правил (разделы «Никогда не пушить
напрямую в main», «Один PR — один коммит», «Code review каждого PR»).
Краткой версии выше достаточно как самодостаточного источника.

## Где живёт знание о проекте (memory-agnostic)

**Главный принцип: всё durable-знание о проекте живёт ВНУТРИ проекта** —
в его репозитории (`CLAUDE.md`, `DECISIONS.md`, `docs/`, `specs/`,
`BOARD.md` / `BACKLOG.md`). Любой **внешний** слой персистентной памяти
ассистента (если он у Разработчика вообще есть — может и не быть) — это
**только опциональный дубль / подстраховка**; методика обязана работать
и БЕЗ него.

Причина двойная:

1. Внешняя память ассистента часто привязана к пути / машине и не
   переносится и не шарится между рабочими копиями (worktree) и
   платформами.
2. Знание о проекте должно уходить вместе с репозиторием любому, кто его
   клонирует.

**Правило:** сначала фиксируй факт в файлах проекта, и только потом
(если такой механизм есть) опционально дублируй его вовне. «Хочешь —
дублируй, но всё о проекте — внутри проекта.»

## Параллельная работа в нескольких git worktree

Несколько задач можно вести **одновременно**, каждую в своём
`git worktree` (отдельная рабочая копия репозитория, общий `.git`),
чтобы не переключать ветки в одном checkout. В такой момент в разных
папках могут параллельно работать **несколько сессий Claude** — по одной
на worktree. Они обязаны знать друг о друге и не сталкиваться.

**Реестр — встроенный `git worktree list`.** Все worktree делят один
`.git`, поэтому из любой папки-клона `git worktree list` показывает ВСЕ
сестринские worktree (путь + ветка + HEAD). Отдельный самодельный
файл-реестр не нужен.

**Ритуал старта.** В начале сессии — `git worktree list` +
`git branch --show-current`. Если worktree больше одного — рядом
**может работать другая сессия** на другой ветке; её путь и ветка =
**чужая территория**.

**Изоляция (жёстко):**

- Один worktree = одна задача = одна ветка. Не чекаутить, не коммитить,
  не ребейзить и не пушить в чужую ветку; не редактировать файлы под
  чужим путём worktree.
- Гейты и тесты гонять из **своего** окружения. Наследованная
  переменная окружения виртуального окружения может указывать на
  окружение **другой** папки — активируй / указывай своё, иначе
  прогонишь проверки не в том окружении.
- **Общие «дописываемые сверху» журналы** (`DECISIONS.md`,
  `CHANGELOG.md`, `BOARD.md`, `BACKLOG.md`) при мерже двух параллельных
  задач конфликтуют почти всегда. Трогай **только запись своей задачи**;
  перед PR обязательно `git fetch` + `git rebase` на свежий `main` и
  разрули конфликты (как правило — сохранить чужие записи, вписать
  свою). Код разных задач обычно сливается чисто — конфликтует именно
  текст журналов.

**Жизненный цикл worktree:**

- Создать: `git worktree add ../<repo>-T<NNN> -b T<NNN>-<slug>` (или на
  существующую ветку).
- Перед PR: `git fetch` → rebase на свежий `main` → squash в один
  коммит (правило «один PR — один коммит») → push → PR → review.
- После merge: `git worktree prune` + удалить локальную ветку.

**Уборка за собой — спросив разрешения.** Закончил задачу или связную
группу задач — **предложи убрать папку-клон** (worktree). Но клон может
содержать нужное (недокоммиченное, локальные заметки, артефакты),
поэтому `git worktree remove` — **только после явного «да»**
Разработчика. Не удаляй молча. Основной checkout и чужие worktree при
уборке не трогаем.

**Общие dev-сервисы — один экземпляр на пользователя.** Если запуск
приложения поднимает общие ресурсы (БД, контейнеры, локальный конфиг,
занятый порт), две параллельные копии их **делят** — расходящиеся
миграции / состояние, конфликт за порт. Предупреди и покажи, как
изолировать (отдельная БД / конфиг / порт на каждый worktree).

**Память ≠ общая между папками.** Файловая авто-память ассистента, если
она есть, обычно привязана к пути cwd: сессия, запущенная **внутри**
папки-клона, получает ОТДЕЛЬНУЮ (пустую) память и НЕ видит память
основной папки. Поэтому durable-знание держи в файлах репозитория (они
есть в каждом worktree) — см. раздел «Где живёт знание о проекте
(memory-agnostic)» выше. По умолчанию предпочитай запуск сессии из
основной папки и работу над worktree через абсолютные пути.

В проекте есть переиспользуемый контур сотрудничества: лид (эта
сессия), read-only субагент-Архитектор и внешний Дизайнер (Claude
